# LineNexus 工业控制平台 — 总体架构设计（草案）

> 状态：草案 / 用于对齐方向，不作为最终实现规格  
> 范围：云平台（Java）+ 边缘网关（Go）+ Docker 协议仿真层  
> 读者：开发、架构、后续接入实现的同学  
> 实现进度：见 `02-开发进展.md`；数据存储约定见 `03-数据存储.md`  
> （边端 SQLite / 云 MySQL / 云 TDengine 已落地）

---

## 1. 背景与目标

LineNexus 面向工业现场的**监控、调度、编排**场景，先用软件仿真把整条链路跑通，再逐步替换为真实设备。

当前阶段的核心目标：

1. 云上提供多租户的监控、任务调度与编排能力。
2. 现场（或实验室）部署 Go 网关，统一南向协议、北向上报。
3. 网关下方用 Docker **批量拉起** Modbus / MQTT / OPC UA / CODESYS PLC 仿真，用于联调、压测和演示。

**非目标（本阶段不做）：**

- 替代 DCS / SCADA 的全套工艺组态与安全认证。
- 直接对接产线真实 PLC 的生产投运（仅预留协议与点表模型）。
- 跨厂级 MES / ERP 深度集成。

---

## 2. 设计原则

| 原则 | 含义 |
| --- | --- |
| 云边分离 | 云负责租户、策略、编排与观测；边负责协议、实时采集、本地缓存与仿真容器生命周期 |
| 协议可插拔 | 南向协议以适配器接入，云侧只看统一点表 / 设备模型 |
| 先仿真后实物 | 仿真设备与真实设备共用同一套设备模型，切换时尽量只改连接配置 |
| 租户隔离 | 数据、任务、网关、仿真资源都带租户边界 |
| 可批量、可回收 | 仿真实例按「实验 / 产线副本」成组创建、扩缩、销毁 |

## 3. 总体架构

```text
┌─────────────────────────────────────────────────────────────────┐
│                     LineNexus Cloud  (Java)                      │
│  多租户 / IAM   资产与点表   监控告警   任务调度   编排引擎         │
│  设备影子       南北向接入   观测与审计   仿真实验管理              │
└────────────▲───────────────────────────────┬────────────────────┘
             │ 心跳 / 遥测 / 事件            │ 指令 / 编排 / 配置下发
             │ MQTT / gRPC / HTTPS           │
┌────────────┴───────────────────────────────▼────────────────────┐
│                   LineNexus Edge  (Go 网关)                      │
│  北向通道   协议适配器   点表映射   本地缓存   Docker 编排器        │
└──────┬──────────┬──────────┬───────────────┬────────────────────┘
       │          │          │               │
       ▼          ▼          ▼               ▼
   Modbus     MQTT Broker  OPC UA      CODESYS SoftPLC
   Slave ×N    + 模拟发布   Server ×N    Runtime ×N
              （均为 Docker 批量实例）
```

逻辑上分三层：

| 层 | 组件 | 职责 |
| --- | --- | --- |
| 云 | `linenexus-cloud` | 多租户、监控、调度、编排、资产、实验管理 |
| 边 | `linenexus-edge` | 协议接入、命令下发、断网缓存、仿真容器管控 |
| 设备 | `linenexus-sim` | 各协议仿真镜像与编排模板 |

仓库建议与现有目录对齐：

```text
LineNexus/
├── doc/                  # 设计文档
├── linenexus-cloud/      # Java 云平台（待建）
├── linenexus-edge/       # Go 网关（已占位）
└── linenexus-sim/        # 仿真镜像、compose、实验模板（待建）
```

## 4. 云平台（Java）

建议技术栈（可替换，先定方向）：

- 应用：Spring Boot 3 + Spring Security
- API：REST + 少量 gRPC（对网关控制面）
- 消息：MQTT（设备通道）+ Kafka（云内异步、告警、审计）
- 数据：
  - 边端 `linenexus-edge`：**SQLite**（现场配置与缓存）
  - 云 `linenexus-cloud`：**MySQL**（业务元数据，当前含网关注册）
  - 时序库：**TDengine**（历史曲线 / 高频采样，与 MySQL 分库）；详见 `03-数据存储.md`
  - Redis（会话、限流、在线态）可后续按需引入
- 任务：调度用 XXL-JOB 或自研轻量调度器；编排用 Flowable / Temporal（二期可换）
- 观测：Micrometer + Prometheus + Grafana + OpenTelemetry

### 4.1 模块划分

```text
linenexus-cloud
├── iam            租户、用户、角色、API Token
├── asset          网关、设备、点表、产品型号
├── ingest         北向接入、鉴权、解码、写入时序 / 影子
├── monitor        实时监视、历史曲线、告警规则、通知
├── scheduler      周期采集策略、巡检、报表、定时启停仿真
├── orchestrator   有向无环工作流：实验、联调、批量操作
├── lab            仿真实验：模板、配额、实例组、端口规划
├── command        写点、调用、程序下装（CODESYS 预留）
└── audit          操作审计、指令回执
```

### 4.2 多租户

采用 **共享库 + `tenant_id` 行级隔离** 作为默认方案，实现简单，适合前期。

约束：

- 所有业务表必须带 `tenant_id`，查询强制注入。
- 网关、设备、点、任务、实验、告警规则均归属租户。
- 跨租户禁止直连；平台超管走独立管理面。
- 配额：每租户网关数、设备数、并发仿真容器数、时序保留天数。
- 后续若有强隔离客户，再拆独立 Schema / 独立库，接口层保持不变。

层级建议：

```text
Tenant（租户）
 └── Site（厂 / 实验室）
      └── Line / Cell（产线或实验单元）
           └── Gateway → Device → Point
```

### 4.3 监控

监控对象分四类，避免只盯「点值」：

1. **遥测**：点值、质量戳、时间戳；实时订阅 + 历史查询。
2. **设备健康**：在线、最后心跳、采集成功率、写成功/失败。
3. **网关健康**：CPU / 内存、通道状态、积压、Docker 引擎是否可达。
4. **仿真资源**：容器状态、端口冲突、镜像版本、实验到期。

告警：阈值、离线、质量坏点、规则表达式。通知先做站内 + Webhook，邮件 / 企微后补。

设备影子（Device Shadow）：云端保留「期望 / 上报」两份状态，网关重连后对账，避免只靠实时流。

### 4.4 任务调度

调度解决「按时间或 cron 反复做同一件事」，与编排区分开。

典型任务：

- 按点表周期采集（也可下沉到网关本地周期，云只下发策略）。
- 定时启停某组仿真容器。
- 巡检：抽检关键点、对账影子。
- 数据清理、报表汇总。

模型：`JobDefinition`（租户内模板）→ `JobInstance`（一次执行）→ `JobLog`。

执行位置：

- **云内任务**：报表、清理、通知。
- **边侧任务**：采集、写点、容器操作。云把任务描述下发，网关执行并回执。

### 4.5 编排

编排解决「多步骤、有依赖、可回滚」的流程，例如一次实验：

```text
申请配额 → 按模板拉起 N 个仿真 → 等待就绪
→ 下发点表 / 采集策略 → 跑测试序列
→ 采集结果归档 → 销毁容器 → 释放配额
```

引擎需求（一期可做简化状态机，不必上重型工作流）：

- 步骤类型：等网关在线、Docker 操作、写点、等条件、人工确认、超时失败。
- 每步有超时、重试、失败策略（继续 / 回滚 / 人工）。
- 全程按租户审计。

调度 vs 编排：

| | 调度 | 编排 |
| --- | --- | --- |
| 形态 | 单任务重复执行 | 多步骤 DAG / 状态机 |
| 例子 | 每 5s 采一次温压 | 拉起 50 个 PLC → 联调 → 销毁 |
| 失败 | 记日志，下次再跑 | 要补偿或回滚 |

## 5. 边缘网关（Go）

`linenexus-edge` 是现场唯一对外进程，云不直接打到仿真容器。

### 5.1 职责

- **注册与心跳**：网关 ID、租户绑定、能力声明（支持哪些协议、能否管 Docker）。
- **配置同步**：点表、采集周期、实验模板、写权限。
- **南向采集 / 写入**：按适配器访问仿真或真实设备。
- **北向通道**：遥测批量上报、事件、指令订阅、回执。
- **断网缓存**：本地 WAL / SQLite，恢复后补传。
- **Docker 编排器**：按云下发的实验规格创建、扩缩、销毁仿真容器。

### 5.2 内部结构

```text
cmd/edge
internal/
├── northbound/     MQTT + gRPC 客户端、鉴权、重连
├── southbound/
│   ├── modbus/
│   ├── mqtt/
│   ├── opcua/
│   └── codesys/    先走 OPC UA / Modbus，再补专用通道
├── mapping/        协议地址 ↔ 统一点
├── cache/          离线队列
├── docker/         容器生命周期、网络、端口、健康检查
└── agent/          心跳、任务执行器、安全沙箱（禁任意镜像）
```

### 5.3 北向协议建议

| 通道 | 用途 |
| --- | --- |
| MQTT | 遥测、事件、轻量命令（主题按 `tenant/gateway/...` 分层） |
| gRPC | 配置全量/增量同步、实验管控、大包回执 |
| HTTPS | 启动注册、证书轮换、人工诊断 |

网关出站即可，实验室环境不必给每个仿真容器公网地址。

### 5.4 安全底线（即使是仿真环境也要有）

- 网关凭据：安装时一次性激活码换长期证书 / Token。
- 写点与 Docker 操作必须带租户、网关、实验三维校验。
- 镜像白名单：只允许预置仿真镜像，禁止跑任意 `docker run`。
- 仿真网络与宿主机管理面隔离（独立 Docker network）。

## 6. 设备仿真层（Docker 批量）

仿真不是「演示玩具」，而是和真实设备共用模型的可复制实验室。

### 6.1 协议与镜像方向

| 协议 | 仿真形态 | 说明 |
| --- | --- | --- |
| Modbus TCP | Slave 容器，可配保持寄存器 / 线圈 | 最容易批量，作第一协议 |
| MQTT | 共享 Broker + 多个发布/订阅模拟器 | 设备用 clientId / topic 区分 |
| OPC UA | Server 容器，暴露节点树 | 地址空间由模板生成 |
| CODESYS | SoftPLC Runtime 容器 | 用 IEC 61131 工程；对外优先 OPC UA / Modbus，避免一上来绑专有协议 |

CODESYS 许可与镜像来源需单独评估：无正式许可时，可用 OpenPLC / 自研软 PLC **占位**，点表和编排接口保持不变。

### 6.2 批量模型

不以「单个容器」为云侧主对象，而以 **实验实例组（Lab Bundle）**：

```text
LabTemplate          镜像、协议、点数、端口策略、默认程序
 └── LabInstance     某租户一次实验
      ├── replicas   副本数（如 20 个 Modbus Slave）
      ├── network    专用 bridge
      └── endpoints  网关实际连接的 ip:port / topic / ua-url
```

网关侧 Docker 编排器负责：

1. 按模板拉镜像（或使用本地缓存）。
2. 分配端口或走容器 DNS（推荐同一 overlay/bridge，网关用容器名访问，少做宿主机端口映射）。
3. 健康检查通过后，把 endpoint 注册回云，并自动生成 / 绑定点表。
4. 到期或编排「销毁」步执行 `stop + rm`，释放配额。

规模预期（设计按此留接口，不必第一天达到）：

- 单网关：约 50～200 个轻量仿真（Modbus / MQTT）。
- OPC UA / CODESYS 更重，副本数单独配额。
- 跨主机扩容：后期加 Docker Swarm / K8s，接口仍是 Lab API。

### 6.3 仿真与真实设备的切换

设备记录上区分 `mode = simulated | physical`，以及 `connection`。

云侧监视、调度、编排只认 `device_id + point_id`。把仿真换成真实 PLC，只需改连接并停掉对应 Lab，不必改业务流。

## 7. 统一数据模型（云边共用概念）

最小集合，避免过早上数字孪生全家桶：

| 对象 | 关键字段 |
| --- | --- |
| Tenant | id, name, quota |
| Gateway | id, tenant_id, status, capabilities |
| Product | 型号、默认点表模板 |
| Device | id, product_id, gateway_id, protocol, mode, connection |
| Point | id, device_id, name, data_type, rw, address, scale |
| Telemetry | device_id, point_id, value, quality, ts |
| Alarm | rule_id, level, state, ts |
| Job / Workflow | 定义、实例、日志 |
| LabTemplate / LabInstance | 仿真规格与运行态 |

点地址按协议放在 `address` JSON 中，例如：

```json
{ "protocol": "modbus", "unitId": 1, "func": 3, "offset": 0, "type": "int16" }
```

## 8. 关键数据流

### 8.1 采集上报

```text
仿真/设备 --协议--> 网关适配器 --规范化 Point--> 本地缓冲
    --MQTT 批量--> 云 ingest --> 时序库 + 影子 + 告警计算
```

### 8.2 写命令

```text
控制台 / 编排步骤 --> command 服务 --> 网关（MQTT/gRPC）
    --> 适配器写入 --> 回执 --> 审计
```

### 8.3 拉起一批仿真

```text
用户选模板 + 副本数 --> 编排创建 LabInstance
    --> 网关 docker 模块创建网络与容器
    --> 健康检查 --> 注册 Device/Endpoint
    --> 下发点表与采集策略 --> 进入监视
```

## 9. 部署拓扑（开发期）

单机即可：

```text
开发机 / 实验室主机
├── PostgreSQL / Redis / MQTT Broker / Kafka（可用 compose）
├── linenexus-cloud（Java）
├── linenexus-edge（Go，调本地 Docker socket）

```

生产雏形：云平台与 Broker 部署在服务器；网关部署在实验室或现场工控机，只出站连云。

## 10. 分期建议

### P0 — 竖切一条链路

- 租户 + 用户登录。
- 网关注册、心跳。
- Modbus TCP 仿真：网关可批量拉起 N 个 Slave。
- 统一点表采集、云上实时监视。
- 手动写 1～2 个点并看回执。

### P1 — 监控与调度

- 历史曲线、基础告警。
- 采集策略与定时任务下发。
- MQTT 仿真（Broker + 模拟发布器）。
- 配额与实验到期回收。

### P2 — 编排与更多协议

- 实验编排状态机（创建 → 运行 → 销毁）。
- OPC UA 仿真。
- CODESYS SoftPLC（或 OpenPLC 占位）+ 工程/程序下装预留。
- 审计与更完整的设备影子对账。

### P3 — 加固

- 时序保留策略细化、边端 outbox 补传冲刷。
- 网关 HA / 多主机仿真。
- 真实设备接入试点。
- 工作流引擎是否上重型产品，按复杂度再定。

## 11. 风险与开放问题

需要在下一轮设计里拍板，本草案不假装已决定：

1. **CODESYS**：用官方 Runtime 还是 OpenPLC 占位？许可如何管理？
2. **时序库**：已定为 **TDengine**（管理 MySQL + 历史 TDengine）。
3. **编排引擎**：P0/P1 自研状态机是否够用，何时引入 Temporal / Flowable？
4. **MQTT 拓扑**：云边共用一个 Broker，还是边侧本地 Broker + 桥接？
5. **仿真网络**：单机 bridge + 容器 DNS，还是宿主机端口映射方便抓包？
6. **多租户网关**：一台物理网关是否允许挂多个租户？（建议一期 **一网关一租户**）
7. **身份**：是否对接现有 SSO，还是先做本地账号。
